# API Synchronizations and Relationships in Noted

This document outlines all the synchronizations and relationships between different API concepts used throughout the Noted application. Use this as a reference when implementing backend synchronization logic.

## Core Entities

### User

* **ID**: Unique identifier (`_id` or user ID string)
* **Username**: Unique username for authentication
* **Password**: Hashed password
* **Session**: Active session token
* **Profile**: Bio, thumbnail URL
* **Friends**: List of friend user IDs (bidirectional)
* **FriendRequests**: Incoming and outgoing friend requests

### MusicEntity

* **ID**: Internal database ID (`_id`)
* **External ID**: Spotify ID (`externalId`)
* **URI**: Spotify URI (`uri`)
* **Type**: `track`, `album`, `artist`
* **Metadata**: name, artistName, imageUrl, description, releaseDate, durationMs, externalURL

### Playlist

* **Owner**: User ID
* **Name**: Playlist name (e.g., "Favorites", "Listen Later")
* **Items**: Ordered list of item IDs (stored as `externalId` from MusicEntity)
* **Note**: Playlists are created automatically when first item is added

### Review

* **ID**: Review ID (`_id`)
* **Author/User**: User ID who created the review
* **Target/Item**: MusicEntity ID (internal `_id` or `externalId`)
* **Rating**: 1-5 star rating
* **Notes/Text**: Review text content
* **Date**: Creation/update timestamp
* **Comments**: Array of comment objects

### Comment

* **ID**: Comment ID (`commentId`)
* **Review**: Review ID this comment belongs to
* **Commenter**: User ID who wrote the comment
* **Notes/Comment**: Comment text content
* **Date**: Creation timestamp

### FriendRequest

* **ID**: Request ID
* **Sender/Requester**: User ID who sent the request
* **Receiver/Target**: User ID who received the request
* **Status**: Pending (implied by existence)

### SearchResult

* **User**: User ID who performed the search
* **MusicEntity**: MusicEntity ID
* **LastQuery**: Most recent search query string

## Entity Relationships

### User ↔ MusicEntity

* **Via Playlists**: Users can add MusicEntities to playlists (Favorites, Listen Later)
* **Via Reviews**: Users can review MusicEntities (one review per user per item)
* **Via Search**: Users have search history linked to MusicEntities

### User ↔ User

* **Friends**: Bidirectional friendship (both users have each other in friends list)
* **FriendRequests**: One-way requests (sender → receiver)

### Review ↔ MusicEntity

* **One-to-Many**: One MusicEntity can have many Reviews
* **Many-to-One**: One Review belongs to one MusicEntity
* **Unique Constraint**: One user can only have one Review per MusicEntity

### Review ↔ Comment

* **One-to-Many**: One Review can have many Comments
* **Many-to-One**: One Comment belongs to one Review

### Playlist ↔ MusicEntity

* **Many-to-Many**: Playlists contain multiple MusicEntities, MusicEntities can be in multiple playlists
* **Storage**: Playlist items are stored as `externalId` (Spotify ID), not internal `_id`

## Synchronization Patterns

### 1. Playlist ↔ MusicEntity Synchronization

**When adding item to playlist:**

* Frontend sends `externalId` (Spotify ID) to backend
* Backend must:
  1. Look up or create MusicEntity using `externalId`
  2. Add the MusicEntity's `externalId` (or `_id`) to playlist items
  3. Ensure playlist exists (create if doesn't exist)

**When removing item from playlist:**

* Frontend sends `externalId` to backend
* Backend must:
  1. Find item in playlist by `externalId`
  2. Remove first occurrence from playlist items array

**When loading playlist items:**

* Backend returns list of item IDs (as `externalId`)
* Frontend then fetches full MusicEntity details using `getEntityFromId(externalId)`
* **Sync Requirement**: Backend must ensure all playlist items reference valid MusicEntities

### 2. Review ↔ MusicEntity Synchronization

**When creating/updating review:**

* Frontend sends `item` (which is `externalId` or internal `_id`)
* Backend must:
  1. Resolve `item` to MusicEntity (by `externalId` or `_id`)
  2. Ensure MusicEntity exists (create from Spotify if needed)
  3. Create/update Review with reference to MusicEntity
  4. Enforce uniqueness: one Review per User per MusicEntity

**When loading reviews:**

* Backend returns Review with `item` field (MusicEntity ID)
* Frontend fetches MusicEntity details separately using `getEntity(item)`
* **Sync Requirement**: All Review `item` fields must reference valid MusicEntities

### 3. Review ↔ Comment Synchronization

**When adding comment:**

* Frontend sends `review` (Review ID) and `commenter` (User ID)
* Backend must:
  1. Verify Review exists
  2. Verify User exists
  3. Add Comment to Review's comments array
  4. Return updated Review with comments

**When deleting comment:**

* Frontend sends `review` (Review ID) and `commentId`
* Backend must:
  1. Verify Review exists
  2. Find and remove Comment from Review's comments array

**Sync Requirement**: Comments must always reference valid Reviews and Users

### 4. User ↔ User (Friends) Synchronization

**When accepting friend request:**

* Backend must:
  1. Add `requester` to `target`'s friends list
  2. Add `target` to `requester`'s friends list
  3. Delete the FriendRequest
  4. **Critical**: Both operations must succeed or both must fail (transaction)

**When removing friend:**

* Backend must:
  1. Remove `friend` from `user`'s friends list
  2. Remove `user` from `friend`'s friends list
  3. **Critical**: Both operations must succeed or both must fail (transaction)

**Sync Requirement**: Friendships must always be bidirectional and consistent

### 5. MusicEntity Creation/Update Synchronization

**When searching:**

* Frontend sends search query
* Backend must:
  1. Search Spotify API
  2. For each result:
     * Check if MusicEntity exists (by `externalId`)
     * If exists: update metadata if needed
     * If not exists: create new MusicEntity
  3. Create SearchResult entries linking User to MusicEntities
  4. Clear old SearchResults for user

**When fetching entity by ID/URI:**

* Backend must:
  1. Look up MusicEntity by `externalId` or `uri`
  2. If not found, fetch from Spotify and create
  3. Return MusicEntity

**Sync Requirement**: MusicEntities should be created on-demand when referenced

### 6. User Profile Synchronization

**When updating profile:**

* Frontend sends `user` ID and `thumbnailUrl` (base64 data URL) or `bio`
* Backend must:
  1. Verify User exists
  2. Update User's profile fields
  3. Return updated profile

**Sync Requirement**: Profile data must always reference valid Users

## Data Flow Diagrams

### Adding Item to Playlist Flow

```
Frontend (externalId) 
  → Backend: addItem(user, externalId, playlistName)
    → Backend: Lookup/Create MusicEntity by externalId
    → Backend: Add externalId to Playlist.items[]
    → Backend: Return success
  → Frontend: Trigger playlistUpdateEvent
  → Frontend: Reload playlist items
    → Backend: getPlaylistItems(user, playlistName)
      → Returns: [{ item: externalId }]
    → Frontend: For each item, fetch MusicEntity details
      → Backend: getEntityFromId(externalId)
        → Returns: Full MusicEntity object
```

### Creating Review Flow

```
Frontend (item=externalId, user, rating, notes)
  → Backend: postReview(item, user, rating, notes)
    → Backend: Resolve item to MusicEntity (by externalId)
    → Backend: Check if Review exists (user, item)
    → Backend: Create Review with MusicEntity reference
    → Backend: Return Review ID
  → Frontend: Reload all reviews for item
    → Backend: getItemReviews(item)
      → Returns: Reviews with item field
    → Frontend: For each review, fetch MusicEntity and User details
```

### Home Feed Flow

```
Frontend: Load feed
  → Backend: getFriends(user)
    → Returns: List of friend user IDs
  → Frontend: For each friend + self:
    → Backend: getUserReviews(userId)
      → Returns: Reviews with item field
    → Frontend: For each review:
      → Backend: getEntity(item) - Get MusicEntity details
      → Backend: getUsername(userId) - Get reviewer username
      → Backend: getThumbnail(userId) - Get reviewer thumbnail
      → Backend: getReviewComments(reviewId) - Get comments
        → For each comment:
          → Backend: getUsername(commenter) - Get commenter username
          → Backend: getThumbnail(commenter) - Get commenter thumbnail
```

## Key Synchronization Requirements

### 1. ID Consistency

**Problem**: Frontend uses both `externalId` (Spotify ID) and internal `_id` interchangeably.

**Solution**: Backend must:

* Accept both `externalId` and `_id` for MusicEntity lookups
* Store playlist items as `externalId` (consistent with API spec)
* When returning data, include both `_id` and `externalId` when possible
* Resolve `externalId` → `_id` internally for database operations

### 2. Playlist Item Resolution

**Problem**: Playlist items are stored as `externalId`, but need to be resolved to full MusicEntity objects.

**Current Pattern**:

* Backend returns: `[{ item: "spotify:track:123" }]`
* Frontend calls: `getEntityFromId("spotify:track:123")` for each item
* Backend must ensure MusicEntity exists for all playlist items

**Sync Requirement**:

* When adding to playlist: Create MusicEntity if it doesn't exist
* When loading playlist: Verify all items have valid MusicEntities
* When MusicEntity is deleted: Handle orphaned playlist items (remove or mark as invalid)

### 3. Review Item Resolution

**Problem**: Reviews reference MusicEntities, but the `item` field might be `externalId` or `_id`.

**Current Pattern**:

* Reviews store `item` field (could be `externalId` or `_id`)
* Frontend uses `getEntity(item)` to fetch details
* Backend must handle both formats

**Sync Requirement**:

* Normalize `item` field to always reference MusicEntity `_id` internally
* When returning reviews, include both `item` (as `_id`) and `itemExternalId` for frontend convenience
* Ensure all Review `item` fields reference valid MusicEntities

### 4. Friend Bidirectional Consistency

**Problem**: Friendships must be bidirectional - if A is friends with B, then B must be friends with A.

**Sync Requirement**:

* Use database transactions for friend operations
* When accepting request: Add to both users' friends lists atomically
* When removing friend: Remove from both users' friends lists atomically
* Validate consistency: When querying friends, verify bidirectional relationship

### 5. Search Result Cleanup

**Problem**: Search results accumulate and need to be cleared on new searches.

**Current Pattern**:

* `search(user, query)` clears old SearchResults and creates new ones
* `clearSearch(user)` explicitly clears all SearchResults
* `getSearchResults(user)` returns current SearchResults

**Sync Requirement**:

* Clear old SearchResults before creating new ones
* Maintain `lastQuery` on User for search history
* Ensure SearchResults reference valid MusicEntities

### 6. Comment Synchronization

**Problem**: Comments are nested within Reviews and must stay in sync.

**Sync Requirement**:

* When Review is deleted: Delete all associated Comments
* When User is deleted: Handle Comments (delete or anonymize)
* When adding comment: Verify Review and User exist
* Comments must always reference valid Reviews

### 7. Profile Data Synchronization

**Problem**: Profile data (thumbnail, bio) must stay in sync with User.

**Sync Requirement**:

* Profile updates must be atomic
* Thumbnail URLs must be validated/stored securely
* Profile data must always reference valid Users

### 8. Session ↔ User Synchronization

**Problem**: Sessions must always reference valid Users.

**Sync Requirement**:

* When User is deleted: Invalidate all Sessions
* When Session is created: Verify User exists
* Session lookups must return valid User or error

## Critical Synchronization Points

### 1. MusicEntity Lifecycle

* **Creation**: On-demand when referenced (search, review, playlist)
* **Update**: When fetching from Spotify (metadata may change)
* **Deletion**: Should cascade to Reviews and Playlist items (or mark as invalid)

### 2. Review Lifecycle

* **Creation**: One per User per MusicEntity (enforce uniqueness)
* **Update**: Same Review ID, update rating/notes
* **Deletion**: Cascade delete Comments

### 3. Playlist Lifecycle

* **Creation**: Automatic when first item added
* **Update**: Add/remove items (maintain order)
* **Deletion**: Cascade delete or preserve items (depends on requirements)

### 4. Friend Lifecycle

* **Request**: Create FriendRequest (one-way)
* **Accept**: Create bidirectional friendship, delete request
* **Remove**: Delete bidirectional friendship
* **Cancel**: Delete FriendRequest

## API Endpoint Synchronization Matrix

| Operation | Affected Entities | Sync Actions Required |
|-----------|------------------|----------------------|
| `addItem` (Playlist) | Playlist, MusicEntity | Create MusicEntity if needed, add to playlist |
| `deleteItem` (Playlist) | Playlist | Remove item from playlist array |
| `postReview` | Review, MusicEntity | Create MusicEntity if needed, enforce uniqueness |
| `updateReview` | Review | Update rating/notes, preserve item reference |
| `deleteReview` | Review, Comment | Delete review, cascade delete comments |
| `addComment` | Review, Comment | Add comment to review's comments array |
| `deleteComment` | Review, Comment | Remove comment from review's comments array |
| `acceptFriendRequest` | User (x2), FriendRequest | Add to both friends lists, delete request |
| `removeFriend` | User (x2) | Remove from both friends lists |
| `search` | User, MusicEntity, SearchResult | Clear old results, create/update entities, link results |
| `updateThumbnail` | User | Update user's thumbnail URL |

## Error Handling and Edge Cases

### Orphaned References

* **Playlist items** pointing to deleted MusicEntities
  * **Solution**: Validate on load, remove invalid items, or mark as "unavailable"

* **Reviews** pointing to deleted MusicEntities
  * **Solution**: Keep review but mark item as "deleted" or prevent MusicEntity deletion if reviews exist

* **Comments** pointing to deleted Reviews
  * **Solution**: Cascade delete comments when review is deleted

### Concurrent Updates

* **Multiple users** adding same item to playlists
  * **Solution**: Use atomic operations, handle duplicates gracefully

* **User deleting item** while another user is viewing playlist
  * **Solution**: Return error or handle gracefully on frontend

### Data Consistency

* **Friendship** exists but one side is missing
  * **Solution**: Validate and repair on access, or use database constraints

* **Review** exists but MusicEntity doesn't
  * **Solution**: Re-fetch from Spotify or mark as invalid

***

## Implementation Recommendations

1. **Use Database Transactions** for bidirectional operations (friends, friend requests)

2. **Implement Cascading Deletes** or soft deletes for related entities

3. **Validate References** before operations (ensure MusicEntity exists before adding to playlist)

4. **Normalize IDs** internally (convert `externalId` to `_id` for database operations)

5. **Cache MusicEntity** lookups to reduce Spotify API calls

6. **Implement Idempotency** for operations that might be retried

7. **Use Database Constraints** to enforce referential integrity where possible

8. **Log Synchronization Events** for debugging and audit trails

***

## Notes

* Frontend uses `externalId` (Spotify ID) for most operations
* Backend should normalize to internal `_id` for database operations
* All entity lookups should handle both `externalId` and `_id`
* Playlist items are stored as `externalId` per API specification
* Reviews store `item` which should be normalized to MusicEntity `_id`
* Friendships must always be bidirectional
* Search results are temporary and user-specific
